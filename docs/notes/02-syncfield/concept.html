1What SyncField does, and what isn't public

SyncField is split into two parts with a clear line between them.

  • The SDK (syncfield-python, Apache-2.0): drives every device through one recording lifecycle, timestamps every sample, plays the chirps, and writes an episode directory. That's all of it: there is no alignment math in the SDK.
  • The sync service: takes the episode directory and aligns the streams "to sub-frame precision" (README). It is not in any public repository. The SDK only refers to it: the docs list a "Sync service REST API", and code comments mention "the syncfield sync API" and "the SyncField Docker container". So it is shipped as a hosted API and/or a container image, with closed source.

The SDK's job is to record the raw evidence faithfully (every timestamp, which clock it came from, how uncertain it is, and shared anchors). Correcting it is left to a later stage that sees the whole episode. A3 in our plan is where we build that later stage ourselves.

2The episode directory and its time fields

One press of Record followed by Stop is one episode. Each episode becomes one directory on disk, named ep_<date>_<time>_<id>/. Lab 1 creates one under labs/output/1_fake_sensor/ (lab 2 under labs/output/2_webcam_mic/), so you can open the files as you read.

The directory holds two kinds of files: one file per device (stream), with a row for every sample that device delivered, and a few files for the whole episode.

One row, several kinds of time

Every stream on one host stamps capture_ns from the same host monotonic clock, so all of them share one clock domain. Two streams' capture_ns values can be compared directly, with no offset or drift to correct between them. This is the 01-time principle of keeping the number of clock domains small.

A device clock, when there is one, goes in its own field next to capture_ns instead of replacing it. SyncField's docstring explains this as keeping "host-arrival quality checks" meaningful: checks that only look at capture_ns, such as the rate and interval statistics lab 3 computes. Summary question 1 asks you to work out why that matters.

sync_point.json holds two clock readings taken at the same moment when the episode starts: monotonic_ns and wall_clock_ns. Inside a host everything uses monotonic time, because it never jumps (01-time section 4). But a monotonic reading alone doesn't say what date it was. The wall-clock reading taken alongside it places the episode in real-world time, so that people, and other hosts, can tell roughly when it was recorded.

3The Stream interface and the session lifecycle

A rig mixes devices that are opened and read in completely different ways. A webcam goes through the OS camera system, a microphone through the audio system, and a glove through Bluetooth or a serial port. The part that runs a recording shouldn't need to know any of that.

The usual answer is an interface, as in Java or Go: define a few methods every device must offer, and write one wrapper per device that implements them. SyncField calls the interface a Stream and each wrapper an adapter. The part that runs the recording, the SessionOrchestrator, only ever calls the interface methods.

Why the lifecycle has separate steps

Opening a device is slow and unpredictable: a webcam can take a second or more before the first frame. If every device were opened only when the user pressed Record, each stream would begin at a different moment, and the first second of the episode would be missing data from some of them.

So the slow part and the fast part are separate steps:

  • Before Record: open every device and let data flow, but only to a live preview on screen. Nothing is written to disk yet.
  • At Record: on every stream, just flip a switch from "preview only" to "preview and write". Flipping a switch takes microseconds, so all streams start writing at nearly the same instant.
  • At Stop: flip the switch back. The device stays open, so the next recording can start without reopening anything.

In SyncField (stream.py)

The interface's five lifecycle methods:

prepare() → connect() → start_recording(session_clock) → stop_recording() → disconnect()
  • prepare(): one-time setup, such as checking permissions or getting a handle to the device.
  • connect(): open the device and start preview. The docs say it "must not write to disk"; anything slow belongs here.
  • start_recording(session_clock): the switch. The docs say it "must be fast and atomic". session_clock carries the episode's start readings and one shared start time, recording_armed_ns, explained below.
  • stop_recording(): switch back and report how the stream finished. disconnect(): close the device.

The session's states

The orchestrator tracks where the whole session is in one state value:

IDLE → CONNECTED → PREPARING → COUNTDOWN → RECORDING → STOPPING → CONNECTED …
(nothing  (devices    (Record      (3, 2, 1   (writing)   (finishing
 open)     open,       pressed;     on screen)              files)
           preview)    getting
                       ready)

After a recording, the session goes back to CONNECTED with the devices still open, ready for the next episode.

What happens when recording starts

Right after the countdown, the orchestrator starts every stream in a deliberate order:

  1. Read the start clocks and get the files ready. It reads the two start readings for sync_point.json (section 2) and creates every stream's row file, before any stream starts. That way the very first sample already has a file to go to. Who writes the rows is section 5.
  2. Read one start time and give it to everyone. It reads the host clock once and gives that same value to every stream. Each stream then knows exactly when "start" was, as one shared value rather than one per stream.
  3. Flip every stream's switch at the same time. It does this on one thread per stream, so a slow adapter can't delay the others.
  4. Undo everything if one stream fails. If any stream fails to start, it stops the ones that did and reports the error. An episode is either recorded by every stream or not at all.
  5. Play the start sound. Only once every stream is recording (section 6), so that the recordings actually contain it.

Step 2 gives each stream one more piece of evidence. Every adapter takes some time between "start" and its first sample, and that time differs per adapter: a camera waits for its next frame, a microphone for its next block. When a stream's first sample arrives, the stream writes down how long after the shared start time that was. This start-up delay is a per-adapter bias, the kind of error that averaging doesn't remove, so it's recorded and the alignment stage can subtract it.

In SyncField (orchestrator.py, clock.py)

  • The start readings are a SyncPoint. The shared start time is recording_armed_ns inside the SessionClock passed to start_recording().
  • Each stream's start-up timing is its recording anchor in manifest.json: armed_host_ns (the shared start time), first_frame_host_ns (its first sample), and their difference, first_frame_latency_ns. The docstring says alignment uses it "to remove per-adapter bias when aligning streams". Lab 3 prints it as "armed → first sample".

4Where timestamps are taken

01-time section 7 asked where along the way from the device to the program the timestamp should be taken. Each of the three adapters in our labs has a different path from the device into the program. SyncField stamps capture_ns at the point where the data comes into its own code.

Webcam

A webcam takes a picture, usually compresses it (for example as JPEG) to fit through USB, and sends it. On the host, the OS camera system receives it, and PyAV, a Python library around FFmpeg, decodes it back into an array of pixels. SyncField's adapter reads that pixel array and stamps it right then, before doing anything else with it.

light hits the sensor → compress → USB → OS camera system → PyAV decode → capture_ns
                      └───────────── all of this delay is inside capture_ns ─────────────┘

SyncField records no camera-side clock for these frames, so capture_ns is the only time a webcam frame gets.

Polling sensor

For simple sensors, the adapter author only writes a function that reads the sensor once and returns the values. In lab 1 that function is make_fake_device()'s read(). SyncField calls it over and over at a fixed rate, on its own thread, and stamps capture_ns as soon as it returns. The function may also return the device's own clock reading; that becomes device_timestamp_ns.

Microphone

Inside the computer, sound is a list of numbers, typically 44,100 per second, each one how far the air pressure was pushed at that instant. A chip next to the microphone, the ADC (analog-to-digital converter), measures the microphone's voltage at that fixed rate and turns each measurement into a number.

The program doesn't ask for those numbers one at a time. The audio system collects them into a block, and when a block is full it hands the block to the program by calling a function the program registered in advance. Such a function is a callback. It's the same shape as registering an HTTP handler: you never call the handler yourself; the web framework calls it whenever a request comes in. Here the audio system calls it whenever a block is ready.

SyncField's microphone adapter asks for blocks of 0.1 s (4,410 numbers) and reads capture_ns each time its callback runs. Every number goes into the .wav file, but a timestamp row is written far less often. The row is really a loudness summary for the on-screen meter (rms, peak), and the adapter skips a block when less than 0.1 s has passed since its last row. Callbacks arrive just about every 0.1 s, so usually every other block is skipped: in a lab 2 run, 28 of 30 gaps between rows were two blocks (8,820 numbers). Each row's frame_number is how many numbers had been recorded so far, so a row says "number N of the .wav file arrived at capture_ns".

The stamp is taken when a block is handed over, after its last number was recorded. So the block's first number is about 100 ms older than the stamp, plus whatever time the audio system took to deliver the block.

All three stamp on arrival

Adaptercapture_ns is readDevice clock
WebcamRight after PyAV hands over a decoded frameNone
Polling sensorRight after the read function returnsOptional, if the read function returns one
MicrophoneWhen the callback receives a 0.1 s block; a row is kept at most every 0.1 s, usually every other blockNone

All three stamp when the data arrives on the host. That keeps everything in one clock domain, at the cost of the arrival delay and its jitter (01-time section 5). A device clock is an optional extra.

The polling loop

Here is the loop that runs the polling sensor's read function at a fixed rate:

In SyncField (adapters/polling_sensor.py, simplified)

def _capture_once(self):
    loop_start = time.monotonic()
    result = self._read()                # the adapter's read function
    ...
    capture_ns = time.monotonic_ns()     # stamp on arrival
    ...                                  # hand the sample on (section 5)
    elapsed = time.monotonic() - loop_start
    time.sleep(max(0.0, self._period - elapsed))   # _period = 1 / target rate

Compare this with the two loops in 01-time lab 2. Labs 1 and 3 here measure how well it holds the target rate.

5Writers and crash safety

Samples now have timestamps. This section covers how they get to disk, and what's left if the recording is cut off by a crash.

Who writes the rows

Adapters don't write rows themselves. Each time an adapter has a sample, it hands it to the orchestrator, again through a callback: the orchestrator registered a "here's a sample" function on every stream. The orchestrator turns the sample into a row and passes it to a writer, an object that owns one stream's row file and appends to it.

adapter's capture loop ──sample──▶ orchestrator ──row──▶ writer ──▶ {stream}.jsonl

The split keeps each part simple. An adapter only deals with its device, and the file format lives in one place, so changing the format means changing the writers, not every adapter. The bulky data, video pixels and audio numbers, is the exception: the webcam and microphone adapters write their own .mp4 and .wav, and only their timestamps go through a writer.

How a write reaches the disk

A write from a program passes through two holding areas before it reaches the disk, much as sound passes through the audio buffer before the speaker (section 6):

program's write()
  └ program's own buffer     memory inside the Python process
     │  flush()               hand it to the OS
     └ OS page cache          memory inside the OS
        │  fsync(), or the OS on its own a little later
        └ disk
  • If the program crashes or is killed: whatever was still in the program's own buffer is lost. Anything already flushed is with the OS, and the OS writes it to disk anyway.
  • If the OS crashes or the power goes out: whatever was still in the page cache is lost too. Only fsync() waits until the data is really on the disk.

The rows are in JSON Lines format: one complete JSON object per line. A crash can cut off at most the line being written. Every line before it is still a complete record, and the file can be read up to that point.

When the disk is slow

Writing and flushing a row usually takes microseconds. But the disk can stall for tens of milliseconds, for example when another program is writing heavily. If the capture loop writes each row itself, the loop stops for that long: it doesn't read the device, the device's own buffer can overflow and drop samples, and the samples that wait get later capture_ns values. The slow disk pushes its delay back into the capture loop. This is called back-pressure.

The fix is to put a queue between the two. The capture loop only drops each row into the queue and goes straight back to the device. A separate writer thread takes rows off the queue and writes them, in batches. If the queue ever fills up, the capture loop doesn't wait. It records the row as lost and moves on, so a full queue shows up as a counted failure instead of a silent delay. The cost: rows still in the queue or not yet flushed are lost if the program crashes.

In SyncField (writer.py, orchestrator.py)

  • StreamWriter writes video and audio streams' .timestamps.jsonl, and calls flush() after every row.
  • SensorWriter writes sensor streams' .jsonl, the same way by default. An adapter can turn on the queue with queue_capacity; rows are then written and flushed in batches, when a batch is full or at least every 0.1 s. The docstring's reason: "so a slow filesystem can't apply back-pressure to a hardware receive loop". SyncField's adapter for OGL's OGLO glove turns it on (a 4,096-row queue, batches of 256); its comment says this cuts a pair of gloves from about 1,750 flushes per second to about 60.
  • SessionLogWriter writes session_log.jsonl and flushes on every event, "so the log survives a process crash mid-recording".
  • None of them calls fsync().
  • manifest.json is written only at stop(). A recording that crashed has rows and a session log, but no manifest.

6The chirp anchor

This section is about a single moment in the capture stage: just after recording starts, the computer plays a short sound through its own speaker. It walks through why, what the sound is, and why knowing when it played is harder than it looks. SyncField's own names only appear at the end, in the boxes marked "In SyncField".

Why make a sound at all

Say a webcam, a microphone and a glove record the moment a hand touches a cup. Each stamps the data when it arrives on the host, and each device takes a different time to deliver: a webcam frame might arrive about 60 ms after the moment, a microphone block about 20 ms, a glove sample about 1 ms. Nobody tells us these delays. So the same physical moment is written down at three different times, and averaging many samples won't fix it: the webcam is late by roughly the same amount every time (a bias), so the average is late too. Averaging only removes delays that wobble randomly around zero (noise).

Film crews solve this with a clapperboard: one sharp "clap" that the camera and the sound recorder both capture. Later, find the clap in each file, and those points are the same instant. This is what 01-time's glossary called an anchor. SyncField's clap is a short sound played through the computer's speaker. Every microphone in the room records it: the host's own microphone, and the microphones of other hosts nearby.

What the sound is: a chirp

To find the sound in a recording, the aligner uses cross-correlation: it takes the known sound, slides it along the recording one position at a time, and at each position scores how much the two look alike. The position with the best score is where the sound is.

The shape of the sound decides how clear that best score is:

  • A plain beep (one fixed tone, say 1 kHz) repeats the same wave every 1 ms. Slide it by 1 ms and it still matches almost perfectly, so the score has many near-equal peaks and the true position is ambiguous.
  • A hand clap is sharp, but its shape differs every time, and nobody records when it happened on the computer's clock.
  • A chirp is a tone whose pitch slides steadily, for example from 17 kHz up to 19 kHz over 500 ms. Every instant has a different pitch, so the recording matches it only at one exact position.
beep  score:  ▁▃▆█▆▃▁▃▆█▆▃▁▃▆█▆▃▁   many similar peaks
chirp score:  ▁▁▁▁▁▁▁▁▁█▁▁▁▁▁▁▁▁▁   one sharp peak

17–19 kHz is near the top of human hearing, so most adults barely hear it, yet laptop speakers and microphones still handle it. An audible preset (400–2500 Hz) exists for when that matters more than silence; lab 2 uses it so you can hear it. A rising chirp marks the start of a recording and a falling one marks the stop.

We also need the time it played

Finding the chirp in a recording gives a position in that file, say 3.2 s into the audio track. To connect that to every other stream, we also need when the sound came out of the speaker, on the host clock. Then "3.2 s into the audio track" equals "host time T", and every track that recorded the chirp can be lined up on T.

The obvious answer, "read the clock when we tell the computer to play", is wrong by several milliseconds or more. To see why, we need to look at how a computer plays sound.

How a computer plays sound

Section 4 showed sound coming in: an ADC turns the microphone's voltage into a list of numbers, 44,100 per second. Playing is the same path in reverse. Each number says how far the speaker cone should be pushed at that instant, and in front of the speaker sits a chip called a DAC (digital-to-analog converter) that turns one number into a voltage exactly every 1/44,100 s. The DAC never pauses and never waits: if the next number isn't ready, the sound glitches.

So the operating system keeps a queue of upcoming numbers in front of the DAC, called the audio buffer. It works like an order queue in a restaurant: a new order (our chirp) is cooked only after the orders already in the queue. The numbers we hand over come out of the speaker only after everything ahead of them has played, which takes from a few to a few tens of milliseconds and differs between machines and devices.

Between our program and the DAC there are several layers, much like the layers between a web app and a network card:

our Python program
  └ sounddevice      a Python library that wraps PortAudio
     └ PortAudio     a C library that hides the OS differences (one API for macOS, Windows, Linux)
        └ Core Audio  macOS's audio system (WASAPI on Windows, ALSA on Linux)
           └ driver   OS code that talks to the actual audio device
              └ DAC → speaker

Callbacks: the audio system asks for the next numbers

On the microphone side (section 4), the audio system calls the program's callback whenever a block of recorded numbers is ready. Playing works the same way in reverse. The program does not push the whole sound down these layers at once; the audio system pulls. Whenever its buffer runs low, it calls the program's callback with an empty block to fill with the next numbers, every few milliseconds, for as long as the sound plays.

Asking "when will this come out?"

Along with each request, PortAudio passes the callback two readings of the audio system's own clock: "now", and "when the block you're filling right now will leave the DAC". Their difference is exactly the buffer wait we couldn't know before. So in the first callback, the one that fills the chirp's first numbers, the program can compute:

sound left the speaker  =  host clock now  +  (DAC time − audio clock now)
                           └ host monotonic    └ "this many ms from now", from the audio clock

The audio system's clock is a different clock domain from the host's monotonic clock, so its absolute values are never mixed with host times. Only the difference is used, a span of a few milliseconds over which drift between the two clocks is negligible (01-time section 3).

Three possible outcomes

That reading isn't always available, so playing the chirp ends in one of three ways:

What happenedTime we can recordHow good
① The audio system reported the DAC timeWhen the sound actually left the speaker (the formula above)Best
② Sound was played, but no usable DAC time: the device or driver reports none (for example both readings come back as 0), or the first callback doesn't arrive within 0.1 sThe host time read just before asking the audio system to playSecond best: too early by the unknown buffer wait
③ No sound was played: chirp turned off, no speaker, or lab 1's silent playerNoneThis host can't act as an anchor

The recorded time is used as the reference for aligning every stream, so a later stage must know which of the three it got. This is the 01-time error-budget idea again: record the value and where it came from, and let the later stage decide how much precision to claim.

In SyncField (tone.py, types.py, orchestrator.py)

  • The callback is a function named callback inside SoundDeviceChirpPlayer.play(), registered with sd.OutputStream(callback=callback). PortAudio's two readings arrive as time_info.currentTime and time_info.outputBufferDacTime.
  • Outcome ① is computed in that callback and stored in the variable hardware_ns: 
    hardware_ns = monotonic_ns_at_callback + (outputBufferDacTime − currentTime) × 1e9
  • Outcome ②'s time is software_ns, read just before the audio stream is created.
  • Which outcome happened is the source tag: "hardware" (①, the time came from the audio hardware side), "software_fallback" (②, the program's own reading used as a fallback; the docs put its precision at about 1 ms jitter), "silent" (③).
  • All three travel together in a ChirpEmission. The orchestrator writes hardware_ns if present, else software_ns, to sync_point.json as chirp_start_ns / chirp_stop_ns, and the tag as chirp_start_source / chirp_stop_source.
  • The start chirp plays about 200 ms after every stream has started (post_start_stabilization_ms), to let the audio pipelines warm up. That's the ~205 ms you see for chirp_start in lab 3's output.

In the overall pipeline: everything above happens in the capture stage and leaves just two values per chirp in sync_point.json. The alignment stage (SyncField's closed sync service; A3 for us) is what later finds the chirp in each audio track and uses those values.
