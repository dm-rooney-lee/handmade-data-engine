1What SyncField does, and what isn't public

SyncField is split into two parts with a clear line between them.

  • The SDK (syncfield-python, Apache-2.0): drives every device through one recording lifecycle, timestamps every sample, plays the chirps, and writes an episode directory. That's all of it: there is no alignment math in the SDK.
  • The sync service: takes the episode directory and aligns the streams "to sub-frame precision" (README). It is not in any public repository. The SDK only refers to it: the docs list a "Sync service REST API", and code comments mention "the syncfield sync API" and "the SyncField Docker container". So it is shipped as a hosted API and/or a container image, with closed source.

The SDK's job is to record the raw evidence faithfully (every timestamp, which clock it came from, how uncertain it is, and shared anchors). Correcting it is left to a later stage that sees the whole episode. A3 in our plan is where we build that later stage ourselves.

One row, several kinds of time

Every stream on one host is stamped with the same host monotonic clock, so they share one clock domain and need no offset or drift correction between them. This is the 01-time principle of minimizing clock domains. A device clock, when there is one, is recorded alongside instead of replacing capture_ns: the docstring says it is kept separate "so host-arrival quality checks keep their original semantics".

sync_point.json pairs monotonic_ns with wall_clock_ns read at the same moment. Within a host, everything uses monotonic. The wall-clock value only places the session in real-world time, so that hosts and humans can roughly line it up.

3The Stream interface and the session lifecycle

Every device is wrapped in a Stream adapter with the same five methods (stream.py):

prepare() → connect() → start_recording(clock) → stop_recording() → disconnect()
 (once)     (preview)     (start writing)          (stop writing)     (close device)
  • connect() opens the device and starts capturing for live preview, but must not write to disk. Anything slow (opening the camera, warming up) belongs here.
  • start_recording() "must be fast and atomic": it just flips a flag so the capture loop starts writing.

The SessionOrchestrator drives every stream through one state machine:

IDLE → CONNECTED → PREPARING → COUNTDOWN → RECORDING → STOPPING → CONNECTED …

Inside start() (orchestrator.py), the order is deliberate:

  1. Take a fresh SyncPoint and open one writer per stream, before any stream starts, so the very first sample has somewhere to go.
  2. Read armed_ns = time.monotonic_ns() once and give the same value to every stream.
  3. Call start_recording() on all streams in parallel, one thread each, so a slow adapter can't delay the others.
  4. If any stream fails, roll back the ones that started and re-raise.
  5. Only then play the start chirp, "so the audio track actually captures it".

Each stream records a recording anchor in the manifest: armed_host_ns (shared) and the host time of its own first frame. The difference, first_frame_latency_ns, is that adapter's observed start-up latency. The docstring says downstream tooling uses it "to remove per-adapter bias when aligning streams".

4Where timestamps are taken

01-time section 7 asked where to stamp. Here is where SyncField does it, per adapter:

Adaptercapture_ns takenDevice clock
Webcam (uvc_webcam.py)Right after a decoded frame comes out of PyAV, before any further processingNone. Includes USB transfer and decode latency
Polling sensor (polling_sensor.py)Right after the user's read() returnsOptional: read() may return (channels, device_ns)
Host microphone (host_audio.py)When the audio callback delivers a blockNone per sample

All three stamp on host arrival. That's simple and puts everything in one clock domain, at the cost of the arrival-latency jitter discussed in 01-time. The device clock is an optional extra.

The polling loop

A PollingSensorStream runs its own fixed-rate loop on a thread:

def _capture_once(self):
    loop_start = time.monotonic()
    result = self._read()                # call the device
    ...
    capture_ns = time.monotonic_ns()     # stamp on arrival
    ...                                  # emit the sample
    elapsed = time.monotonic() - loop_start
    time.sleep(max(0.0, self._period - elapsed))

Compare this with the two loops in 01-time lab 2. Lab 1 and lab 3 here measure how well it holds the target rate.

5Writers and crash safety

The orchestrator gives each stream a writer by kind (writer.py):

  • StreamWriter (video/audio/custom → .timestamps.jsonl): writes one JSON line per frame and calls flush() after every line.
  • SensorWriter (sensor → .jsonl): the same by default. High-rate adapters can opt into a queue so JSON encoding and batched flushes run on a separate writer thread, "so a slow filesystem can't apply back-pressure to a hardware receive loop".
  • SessionLogWriter: flushes on every event, "so the log survives a process crash mid-recording".

JSON Lines is a good fit for this: every line is a complete record, so a crash loses at most the last partial line, and the file can still be read up to that point.

flush() hands the data from Python's buffer to the OS, which survives the process crashing. It is not fsync(): if the OS crashes or the power goes out, data still in the OS's page cache can be lost.

manifest.json is only written at stop(). A crashed recording has timestamps and a session log but no manifest.

6The chirp anchor

01-time's glossary defined an anchor as a physical event recorded by all streams at once. SyncField's anchor is a sound (tone.py):

  • A chirp is a linear frequency sweep: the default start chirp rises from 17 kHz to 19 kHz over 500 ms; the stop chirp falls back. 17–19 kHz is nearly inaudible to adults but survives a laptop speaker, microphones, and AAC encoding. An audible 400–2500 Hz preset also exists.
  • A sweep is used rather than a plain beep because its cross-correlation has a single sharp peak: slide the known chirp along a recorded audio track and the match is strong at exactly one offset. The comment claims sub-millisecond anchoring.
  • The chirp plays after every stream is writing, so every microphone in the room (on this host and on other hosts) records it.

When did the chirp actually play?

Calling "play" is not the moment sound leaves the speaker. The audio driver buffers samples first. So the player asks PortAudio for the DAC time, which tells it when the first sample will actually leave the digital-to-analog converter:

hardware_ns = monotonic_at_callback + (outputBufferDacTime − currentTime) × 1e9

The result is tagged with its source, so a later stage knows how much to trust it:

chirp_start_sourceMeaning
hardwareFrom the driver's DAC time. The best SyncField can do
software_fallbackThe driver gave no DAC time, so it uses the time just before the play call (~1 ms jitter)
silentNo sound was played (lab 1). This host can't serve as an acoustic reference

With chirp_start_ns (when the chirp left this host's speaker, in host monotonic time) and an audio track that recorded it, an aligner can find the chirp's position in each track and line the tracks up. This is the same idea as the 01-time error budget: record the value, record where it came from, and let the later stage decide how much precision to claim.

8Glossary

episodeOne recording: one directory with every stream's files and the session metadata
Stream (adapter)A wrapper that gives one device the common five-method lifecycle
SessionOrchestratorDrives all streams through one state machine and owns the writers
sync pointA monotonic and a wall-clock reading taken at the same moment at session start
recording anchorA shared arm time plus each stream's first-frame time, used to estimate per-adapter start-up latency
JSON Lines (JSONL)One complete JSON object per line; append-friendly and robust to a crash mid-file
flush vs fsyncflush hands data to the OS (survives a process crash); fsync forces it to disk (survives an OS crash or power loss)
chirpA frequency sweep whose cross-correlation has a single sharp peak, used as an acoustic anchor
cross-correlationSliding a known signal along a recording and measuring the match at each offset; the peak gives the offset
DAC timeWhen the audio hardware will actually output a sample, as reported by the driver
